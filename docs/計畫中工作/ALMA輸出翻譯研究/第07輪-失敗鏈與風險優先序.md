# ALMA 輸出翻譯研究：第 07 輪

> 日期：2026-08-17（Asia/Taipei）
> 階段：FMEA 式 failure chain、控制面與敏感度分析。
> 狀態：發散/反證階段的最後一輪；尚未決定最終方案。

## 本輪問題

1. 一個 ALMA state 從 HTTP 到玩家台詞，最危險的 failure chain 是什麼？
2. 哪些錯誤能在 Renderer 前確定攔截，哪些只能量測/降級？
3. 哪些控制措施同時適用 S1–S8，哪些是某一方案新增的負擔？
4. 在 baseline、secondary cap、staleness、provider failure 等未定參數下，方案排名是否穩健？
5. 第 08–09 輪進入架構整合前，哪些風險必須先被設計消除？

## 本輪讀取的專案證據

- 目前 `chat_service.go` 把 map 直接串成 prompt，既無穩定排序也無 translator/validator 邊界；一個錯誤可從 domain 無阻擋傳到玩家。
- 現有 `llm.Router` 對任意 error 自動換 provider但不回報路由；若未來 Final Renderer 使用 Router，模型差異、capacity 與真正 provider outage 會混在一起。
- `Limiter` 的 `ErrBusy` 是刻意 fail-fast，comment 明示 caller 不應 retry；不區分它與 remote error 會造成 retry storm 或錯誤 fallback。
- 主文件草案的 `RendererAffectContext` 含 `approach_or_withdraw`、`openness`、`response_energy`，但沒有已驗證映射；第 03–05 輪顯示這些容易把狀態擴張成行為決定論。
- 主文件建議例句「責備感」「說話較警戒、反應偏快」超過 ALMA label/PAD 可直接保證的內容，需要在收斂時修正。
- 第 06 輪證實目前 client instrumentation 無法支援 usage、TTFT、route/model provenance；deployment monitoring 不能直接沿用現有回傳介面。

## 外部來源與日期

讀取日期均為 2026-08-17：

- NIST 官網亦標示 AI RMF 1.0 正在修訂；因此本文 pin 到 1.0，不把網頁的未來版本內容當既定要求。

## 評分方法與限制

本輪沒有 production incident 或 E2 實測率，故不計算看似精確的 `severity × occurrence × detection` RPN。只用 ordinal priority：

- **影響 I**：`高` 可造成玩家可見的新事實/關係/意圖、安全邊界或整輪不可用；`中` 造成情緒失真/角色不穩/顯著延遲；`低` 主要為格式或診斷品質。
- **證據 E**：`已證實` 由 source/code contract直接成立；`強假設` 有明確 mechanism但待 E2；`待量測` 無法由靜態分析判斷。
- **前置可偵測 D**：`易` 可在 Renderer 前用 type/assertion擋；`中` 需跨層 metadata/validator；`難` 只在自然語言輸出或玩家影響後出現。
- **優先序 P0–P3**：P0 必須在架構中消除/隔離；P1 上線前要有控制與 regression；P2 要監測/校準；P3 暫留 backlog。

P0 不等於發生率最高，而是後果高且若不在設計期處理會穿透整條鏈。

## 端到端 failure chain

```text
ALMA runtime config/state
  → REST serialization/transport
  → wire decode/contract validation
  → canonical domain mapping
  → target binding + selection/bucketing
  → lexicon/composition/serialization
  → context assembly + precedence
  → Final Renderer/provider
  → post-response checks/logging
  → player-visible reply
```

理想控制順序：越接近來源越早丟棄不可信內容；自然語言層只接收 canonical、bounded、typed facts。後置 response validator是最後保險，不能取代前置資料隔離。

## P0 控制集合

上表的 P0 可濃縮成七個不可妥協的架構條件：

1. **Untrusted wire containment**：完整 decode、limits、unknown/raw/elicitor 隔離。
2. **Canonical state**：relative intensity、stable order、sentinel、paused/timing 與 role match。
3. **Evidence-bound semantics**：typed/versioned lexicon；target 必須 explicit binding。
4. **No unproven behavior derivation**：v1 不把 PAD/emotion固定映成接近、音量、透露、暴力等動作。
5. **Layered precedence**：facts/persona/relationship 授權內容；affect只能調整表達條件。
6. **Fail-safe degradation**：last-good有 age bound；否則 no-affect path，不把 unknown變 neutral fact。
7. **Traceable execution**：route/model/version/attempt/validation reason可觀測，但不記 key/raw private content。

任何候選若必須破壞其中一項才能運作，就不應進第 08 輪整合。

## 敏感度分析

### Secondary cap `N`

| N | 忠實度 | token/注意力 | 已知風險 |
|---:|---|---|---|
| 0 | 丟失 coexistence | 最低 | mood/dominant 過度單一化 |
| 1 | 保留一項對照 | 低 | equal tie需穩定規則 |
| 2 | canonical fixture足夠 | 中 | 仍 bounded，可測 |
| 3+ | 更完整 | 高 | 噪音/重複/小模型遵循下降 |

目前沒有 E2 證據選定 N。第 08 輪可把 `N=2` 當可配置初始值而非心理學真理，並以 relative gap/最低 bucket 排除微弱尾項。

### Strength thresholds

只要所有方案共用同一 bucket service，閾值改變不應改變 S2/S4/S6 相對結構；它主要影響角色反應強度。應用 boundary sweep，尋找微小數值變動造成 wording跳級的位置。不要按 emotion type 各自校準，除非有獨立證據，否則維護面爆炸。

### Staleness age

age bound 太短會頻繁 no-affect，太長會使用過時情緒。ALMA response無 server timestamp，只能從 request success與 computation status建立保守 policy；產品 latency/turn cadence決定數字，本研究不能憑空填秒數。

### Context format × model size

- 大模型可能同樣理解 S4/S6；小 2B 模型可能受 JSON key、nested constraint與長 system rule影響。
- 這是 R25 的待量測 interaction，不能從 parameter count直接定案。
- 若 2B 在所有格式皆高 fail，不表示 translator 無解；可能代表 Final Renderer model低於任務需求。

### Provider availability/cost

S1–S6 translation 本身 offline，provider outage只影響 Final Renderer；S7/S8 多一個依賴使 availability相乘且增加 tail。即使 routed rate低，P95/P99與特殊 case仍承受完整額外 call。

## 風險與失敗模式

- 本輪 rating是 ordinal engineering judgment，不是 incident frequency或量化風險。
- P0 清單偏保守，可能降低戲劇性；產品若要放寬，需明示 risk tolerance與 evidence，不應由 translator暗中決定。
- logging既要足夠診斷又不能保留玩家/elicitor敏感內容，需單獨 threat/privacy review。
- hosted provider無法完全 pin weights；回歸測試只能偵測變化，不能保證重現。
- response post-check很難證明「沒有委婉新增動機」，人工/evidence-span eval仍必要。
- no-affect degradation提高可用性，但可能令角色在故障期間較平；這應被 observability揭露而非填假 neutral。
- 風險 register會隨真正 Final Renderer與資料契約實作而改變；第 10 輪只能提出初始 baseline。

## 本輪改良

- 建立 40 項 FMEA register與七項 P0 architecture control。
- 修正「neutral fallback」：無資料是 unavailable，不是角色心理 neutral。
- 將 expression guidance從預設輸出降為未驗證、預設關閉。
- 定義 role-name match、body/list limits、route reason、attempt denominator等先前遺漏控制。
- 給 secondary cap、bucket、staleness、model interaction 可驗證的敏感度方向。
- 未新增第九方案、未呼叫模型、未修改 production code或設定。

# ALMA 輸出翻譯研究：第 01 輪

> 日期：2026-08-17（Asia/Taipei）
> 階段：問題定義與候選空間；本輪刻意不選定方案。
> 研究對象：ALMA `GET /affect/{character}` 到 Final Renderer `{{alma_context}}` 的轉譯。

## 本輪問題

1. AffectBridge 現在真正需要翻譯的是什麼，而不是抽象的「把情緒變成文字」？
2. ALMA 回應中的 emotion、mood、PAD、baseline、tendency 與 personality，哪些能直接支持表達指引，哪些只能保留為狀態？
3. 在不提前定案的前提下，可形成哪些彼此有實質差異、可以比較與淘汰的方案？
4. 後續九輪要用什麼證據與一致尺度比較？

## 本輪讀取的專案證據

- `ALMA輸出翻譯.md` 已提出正確的兩層邊界：ALMA wire DTO → `AffectSnapshot` → `RendererAffectContext`，但強度門檻、secondary emotion 數量、PAD 用法、趨勢、失敗策略與 expression guidance 還未定。
- `ALMA翻譯系統.md` 約束輸出翻譯不得重新 appraisal，也不得從 emotion 反推事件事實或動機。
- `docs/architecture.md` 要求 raw ALMA payload 只能存在 `internal/affect/alma`，不得成為公開 API contract。
- `docs/最後一層renderer.txt` 目前只提供一個自由文字槽 `{{alma_context}}`；其後另有「習慣表現與用語」區塊。因此情緒層不應吞掉角色慣用語、行為習慣或記憶層的責任。
- `internal/affect/alma/client.go` 仍呼叫尚未證實存在的 `/apply`，並以 `model.Character` 當 wire response；`Snapshot` 只是回傳傳入值。這與目前 ALMA REST 設計及規劃文件有明確落差。
- `internal/service/chat_service.go` 仍直接把 PAD 小數與未排序的 emotion map 塞入 prompt，沒有 `AffectSnapshot`、穩定排序、baseline 判斷、token budget 或 renderer-safe wording。
- `internal/model.Character` 只有簡化 PAD 與 `map[string]float64`，不足以保存 ALMA 的 dominant、baseline、active、mood word、tendency、default mood 及觀測狀態。

以上表示目前研究是在定義未來 contract，不是替已完成的 mapper 選幾個形容詞。

## 外部一手證據與解讀

### ALMA REST 原始實作

ALMA fork 的 `AlmaRestServer.java` 是目前 wire contract 的直接證據：

- `dominant_emotion` 不是單純取最高 raw number 後交給 AffectBridge；server 先取得 emotion vector 的 dominant，若其 intensity 等於 baseline，會改取 `Undefined`。
- `active` 的 server 定義是嚴格的 `intensity > baseline`。
- emotion PAD 對一般 OCC emotion 來自 ALMA 的固定 `EmotionsPADRelation`；只有 `Physical` emotion 使用該 emotion 自帶 PAD。
- `mood`、`mood_tendency` 與 `default_mood` 是三個不同欄位；tendency 取得失敗時，server 會退回 default mood。
- server 在同一組 lock 下組出 dominant 與 emotion list，避免 decay 讓同一 response 自相矛盾。

來源：[ALMA `AlmaRestServer.java`](https://github.com/KuangWei-hash/ALMA/blob/master/src/de/affect/rest/AlmaRestServer.java)（讀取日期 2026-08-17）。

這些事實否定兩個危險捷徑：不能用 `intensity > 0` 自行定義 active；也不能把一次 response 內 dominant 與 emotions 的差異先假設為 race condition。

### ALMA 分層模型

ALMA 原始論文把 personality、mood、emotion 分別視為長期、中期、短期 affect，runtime 以 appraisal 產生 emotion 與 mood。這支持在 renderer contract 中保留時間尺度邊界，而不是把三層合成一句未標來源的心理結論。

來源：Patrick Gebhard, [“ALMA – A Layered Model of Affect”](https://citeseerx.ist.psu.edu/document?doi=679bfc64621dae3a2247be838d042643840961b3&repid=rep1&type=pdf), AAMAS 2005（讀取日期 2026-08-17）。

### PAD 與表達行為

PAD 的三軸是 pleasure、arousal、dominance，而不是已經計算好的「親近、語速、透露意願」。Mehrabian 的三維框架支持 PAD 作為情緒狀態描述；但 approach/avoidance 實驗指出 approach 不只由 pleasure 決定，還有 pleasure × arousal 的交互作用與非線性結果。因而 `approach_or_withdraw = sign(pleasure)` 之類的單軸規則沒有足夠證據。

來源：

- Albert Mehrabian, [“Framework for a comprehensive description and measurement of emotional states”](https://pubmed.ncbi.nlm.nih.gov/7557355/), 1995。
- James A. Russell & Albert Mehrabian, [“Approach-Avoidance and Affiliation as Functions of the Emotion-Eliciting Quality of an Environment”](https://doi.org/10.1177/0013916578103005), 1978。

## 不可違反的語意邊界

1. **狀態不是事實**：fear 不能推出「玩家威脅了角色」。
2. **狀態不是意圖**：hostile mood 不能推出「角色打算攻擊」。
3. **表達傾向不是必然行為**：高 arousal 可支持較高反應能量，但不能直接指定台詞長度、動作或是否坦白。
4. **personality 不重複注入**：若基本角色 context 已提供人格，ALMA response 中 personality 預設只供一致性/診斷，不每輪重複塞進 `alma_context`。
5. **時間尺度不合併**：短期 emotion、當前 mood、default mood、mood tendency 必須能分辨。
6. **單一 snapshot 不提供導數**：沒有前一觀測與可靠時間資訊時，不得描述「正在增強／正在消退」。
7. **server active 定義優先**：使用 `intensity > baseline`，不能另創 `intensity > 0`。
8. **未知值不猜**：未知 enum 保留、告警或降級，不能用字面相似度擅自翻譯。

## 八個候選方案（尚未排序）

本研究最多保留以下八種；後續可以合併或淘汰，但不再無限制增加近似變體。

### S1：最小結構直傳

只傳 current mood word/intensity、dominant emotion/active 與最多 N 個 secondary emotion；renderer prompt 解釋欄位語義。

- 優點假設：最少推論、token 小、忠實。
- 可證偽點：小模型可能無法穩定把 OCC enum 轉成自然表達；prompt 可能洩漏內部術語。

### S2：確定性中文語意字典

每個 ALMA emotion、9 mood words、離散強度映射成中性中文描述，不產生行為指令。

- 優點假設：完全可測試、無額外 LLM、語言自然度較 S1 高。
- 可證偽點：固定文字可能僵硬，且 emotion 組合容易形成互相衝突的句子。

### S3：確定性「表達旋鈕」編譯器

先把狀態編譯成有限、正規化的 renderer controls，例如 valence、energy、assertiveness、emotional pressure；每個 control 必須有明確來源與 clamp 規則。

- 優點假設：比情緒詞更直接控制 renderer，又維持可測試性。
- 可證偽點：PAD 到行為的映射可能過度簡化；controls 可能與角色習慣區塊重疊。

### S4：規則式情緒組合語法

使用 dominant + secondary + mood 的有限語法，明示「背景 mood／短期 emotion／並存或張力」，不把組合壓成新心理標籤。

- 優點假設：保留層次與混合情緒，比逐項列表更容易被 renderer 使用。
- 可證偽點：組合規則數量膨脹；dominant 與 mood 衝突時措辭仍可能暗示不存在的原因。

### S5：模板庫加情境安全變體

在 S2/S4 上為同一結構準備多個等價模板，以 request-stable seed 選擇，降低機械重複但保持重現性。

- 優點假設：在無額外模型下改善自然度。
- 可證偽點：變體只是表面多樣化，增加測試面且可能引入語義漂移。

### S6：結構化資料 + Renderer 原生規則

不先組自然語言；把嚴格 JSON 或明確標記區塊直接放入 renderer prompt，並在 renderer system prompt 定義使用規則。

- 優點假設：避免「文字翻譯層」二次詮釋，可保留 provenance。
- 可證偽點：現有 renderer 只有文字 placeholder；小模型對長 schema 或 nested JSON 的遵循可能較差。

### S7：受約束 LLM wording layer

確定性 mapper 先產生 immutable facts，再由額外 LLM 只自然化文字；用 schema、欄位回顯或後置 validator 保證不能改變 kind、active、strength。

- 優點假設：跨語言與自然度最好。
- 可證偽點：增加 latency、cost、失敗面；即使 schema 合法仍可能語意添油加醋。

### S8：混合式分級策略

正常已知狀態使用確定性編譯；只有未知 enum、複雜混合或指定語言需要自然化時才走受約束 wording，失敗回到最小結構。

- 優點假設：兼顧可靠性與長尾覆蓋。
- 可證偽點：routing 本身可能造成同一狀態輸出風格不一致，且未知 enum 交給 LLM 猜測違反邊界，可能只能告警而不能 wording。

## 統一評估框架

後續各輪使用 1–5 分，但必須附證據或 fixture，不能只靠印象。初期不設定總分冠軍，避免權重偷偷代替產品決策。

| 維度 | 驗證問題 | 最低不可接受條件 |
|---|---|---|
| 語義忠實度 | 是否只陳述 snapshot 支持的狀態？ | 增加原因、事實、意圖或不存在的趨勢 |
| 情緒/人格一致性 | 是否區分短期 emotion、中期 mood、角色風格？ | 把 mood 當事件或重複覆蓋 persona |
| 可控性 | 相同輸入是否穩定，規則能否版本化？ | 同 snapshot 產生相反 guidance |
| 延遲 | 是否增加模型 call 或大量 token？ | 阻塞角色回應且無降級 |
| token/成本 | 每輪固定與變動開銷為何？ | raw payload 或完整 history 無上限進 prompt |
| 結構可靠性 | null、unknown、baseline-only、mixed state 是否安全？ | parse 失敗後把 raw JSON 交 renderer |
| 部署 | 本地/遠端 LLM、離線時是否可工作？ | 翻譯層成為無必要的單點依賴 |
| 可測試性 | 能否建立 golden/contract/metamorphic tests？ | 只能人工主觀判斷 |
| 維護性 | 新 enum、語言、renderer 版本如何演進？ | 變更 wire DTO 直接破壞 public/renderer contract |

## 首批必要 fixture 類別

1. neutral/default，沒有 active emotion。
2. baseline-only emotion（`intensity == baseline`）。
3. 單一 active dominant emotion。
4. dominant + 同方向 secondary emotions。
5. dominant + 衝突或不同時間尺度的 mood。
6. 多個 intensity 接近的 active emotions。
7. `dominant_emotion = null` 或 `Undefined`。
8. unknown emotion/mood enum。
9. `mood_tendency == default_mood`（可能是 server fallback，不能宣稱真實趨勢）。
10. paused snapshot 與過期 snapshot。
11. extreme PAD 邊界與非有限數（adapter 必須拒絕非 JSON 合法/超界值）。
12. 重複讀取同一 snapshot 的 deterministic output。

## 本輪比較結果

本輪不產生總排名。可以先確定：

- S1–S6 都可在沒有額外 LLM call 時運作；S7 明確增加一次 call；S8 視 routing 而定。
- S2、S3、S4、S5 並非互斥，可能是同一 deterministic compiler 的不同輸出層；後續必須避免把相近組合偽裝成多個獨立方案。
- S3 的風險最高集中在「心理狀態 → 行為」的證據缺口，不能因名稱像 control 就視為可靠。
- S7/S8 必須證明自然化收益大於 latency 與語義漂移，不能以「LLM 比較自然」直接勝出。
- S6 與現有 renderer template 的整合成本需要實測小模型與 Groq 模型的遵循度；目前沒有證據。

## 與研究前初稿的差異

1. 初稿只有一條確定性 mapper方向，本輪展開為最多八個可證偽候選，避免先決定再找理由。
2. 把 `expression_guidance` 從看似既定功能降為需證據驗證的假設，尤其不預設 PAD可直接決定接近、透露或行為。
3. 把現行 `/apply`、local `model.Character`與 raw PAD/map prompt的程式落差納入研究範圍。
4. 建立九維比較與十二類 fixture，使後續每輪能對前一輪提出反證與改良。

## 風險與失敗模式

- **來源版本風險**：專案規劃引用的是 KuangWei-hash/ALMA fork；原始 2005 ALMA 論文不能替代此 fork 的 REST wire contract。
- **dominant 語義風險**：server dominant 的排序細節仍需讀 `EmotionVector` 實作，不能只從 list 最後一項推測排序規則。
- **tendency 可信度風險**：reflection 失敗時 server 回 default mood，wire response 沒有標示 fallback；mapper 無法只靠值分辨「真 tendency」與「fallback」。
- **PAD 過度解讀**：文獻支持維度描述，不自動支持每個對話行為旋鈕。
- **狀態新鮮度**：目前草案有 `observed_at`，但 wire response 沒有 snapshot timestamp；只能在成功接收時由 AffectBridge 標記 observed time，不能當成 ALMA 計算時間。
- **map 非確定性**：目前 Go `EmotionSet` 格式化沒有排序，golden output 與 prompt 順序會漂移。

## 本輪改良

相較主文件的初步設計，本輪新增：

1. 明確區分 fork wire source 與理論來源。
2. 將 `active = intensity > baseline`、dominant baseline handling 與 tendency fallback 納入 contract 風險。
3. 把「PAD → expression guidance」從預設設計降為待驗證假設。
4. 固定最多八個候選方案，並為每個方案寫可證偽點。
5. 建立九維評估框架與十二類必要 fixture。
6. 記錄現行程式與規劃的真實落差，避免把研究誤當成單純文案工作。

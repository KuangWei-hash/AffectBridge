# ALMA 輸出翻譯研究：第 04 輪

> 日期：2026-08-17（Asia/Taipei）
> 階段：候選表示格式、靜態大小、token/cost/latency 模型與非付費測試設計。
> 狀態：完成發散階段，但仍不選定最終方案。

## 本輪問題

1. 八個候選方案對同一 `AffectSnapshot` 實際會產生什麼 payload？
2. 它們增加多少 prompt 大小、模型 call、輸出 generation 與失敗面？
3. Groq `qwen/qwen3.6-27b` 與 LM Studio 對 JSON/JSON Schema 的保證是否相同？
4. 不呼叫付費 API，能先驗證哪些 determinism、size 與 schema 性質？
5. 哪些方案應進入第 05–07 輪的行為 fixture，而不是現在靠印象定案？

## 本輪讀取的專案證據

- `config.json` 目前使用 Groq `qwen/qwen3.6-27b`、`reasoning_effort=none`；此檔已有使用者未提交修改，本輪不變更。
- `internal/llm/pgedge.go` 可以送 `json_schema` response format，但 provider/model 是否真的支援仍由遠端決定；wrapper 本身不會把 best-effort 變成 strict guarantee。
- `docs/最後一層renderer.txt` 的 `{{alma_context}}` 位於大型 system/template context 中。本輪只量測 affect 區塊的**邊際大小**，不把它誤報為整個 request token 數。
- 第 02 輪定義 canonical domain；第 03 輪定義 target-neutral lexicon。任何表示格式都必須先通過這兩層，不能直接從 raw JSON 拼 prompt。
- 目前 Final Renderer 尚未真正使用 `最後一層renderer.txt`；`chat_service.go` 仍直接傳 PAD/EmotionSet。因此本輪 payload 是研究 fixture，不代表已部署格式。

## 外部官方來源與日期

讀取日期均為 2026-08-17：

- [Groq Supported Models](https://console.groq.com/docs/models)：`qwen/qwen3.6-27b` 目前列為 preview，官方標示約 500 tokens/s、input `$0.60/M`、output `$3.00/M`、131,072 context、16,384 max completion。
- [Groq Structured Outputs](https://console.groq.com/docs/structured-outputs)：strict JSON Schema 目前只列 GPT-OSS 20B/120B；其他未列模型使用 JSON Object Mode，只保證 JSON object，不保證符合任意 schema。
- [Groq Tool Use / model capability table](https://console.groq.com/docs/tool-use/overview)：`qwen/qwen3.6-27b` 支援 JSON mode，但不因此取得 strict schema guarantee。
- [Groq Latency Guide](https://console.groq.com/docs/production-readiness/optimizing-latency)：input tokens 影響 TTFT；總延遲應拆為 TTFT + output tokens / generation speed + network round trip。
- [LM Studio Structured Output](https://beta.lmstudio.ai/docs/developer/openai-compat/structured-output)：local server 可在 `/v1/chat/completions` 接受 JSON Schema 並約束 JSON 結構。

重要限制：JSON Schema 只能驗證 type/shape/enum 等結構，不能證明自由文字欄位沒有增加原因、對象、意圖或行為。這點對 S7 特別關鍵。

## 共用 canonical snapshot

本輪所有候選都由同一份已通過 mapper 的資料產生：

```text
current mood
  label=Anxious
  strength=moderate
  PAD=(-0.40, +0.50, -0.20)

dominant emotion
  kind=Fear
  strength=strong
  target=unknown

secondary emotions
  Anger, moderate, target=unknown
  Hope, slight, target=none

constraints
  no cause supplied
  unknown target must not bind to current player
```

這個 fixture 刻意同時有 mood、dominant、target-sensitive secondary 與非 target-specific secondary，以暴露格式差異。

## 八種具體候選表示

### S1：最小 enum 直傳

```text
mood=Anxious:moderate; dominant=Fear:strong:target_unknown; secondary=Anger:moderate:target_unknown,Hope:slight:target_unknown
```

優點是短；缺點是 Renderer 必須記得所有 enum 語義，且英文 `Anxious/Anger` 容易觸發日常刻板行為。

### S2：typed lexicon 中文短語

```text
整體心境：中等程度的不愉快、活躍、掌控感較低。主要情緒：強烈的擔憂，原因未指明。次要情緒：中等程度的生氣與輕微期待；生氣的對象未指明。
```

所有詞由第 03 輪 lexicon 產生；沒有因果連接與具體 target。

### S3：表達旋鈕

```text
affect_controls: valence=-0.40; energy=0.50; control=-0.20; pressure=strong; target_binding=unknown
```

格式很短且 deterministic，但 `energy/control/pressure` 是否能安全控制對話行為仍未證實；它也丟失 Fear/Anger/Hope 的 appraisal focus。

### S4：分層組合語法

```text
整體心境偏向中等程度的焦慮不安（不愉快、活躍、掌控感較低）。短期主要情緒是強烈擔憂；同時存在中等生氣與輕微期待。情緒的具體原因與生氣對象未提供，不可假定與目前玩家有關。
```

明確區分 mood/short-term emotion 並附 target constraint，代價是字數較多。

### S5：stable-seed 模板變體

```text
目前的整體心境帶有中等焦慮：感受偏負向、反應能量較高、掌控感較低。短期內以強烈擔憂為主，也夾有中等生氣和些許期待。相關原因及生氣對象未知，勿綁定目前玩家。
```

這是 S4 的等價模板候選，不代表已證明語意等價。「反應能量」比單純 `arousal` 多一層解釋，必須在後續測試。

### S6：typed compact JSON

```json
{"mood":{"label":"Anxious","strength":"moderate","valence":"negative","energy":"high","control":"low"},"dominant":{"kind":"Fear","strength":"strong","target":"unknown"},"secondary":[{"kind":"Anger","strength":"moderate","target":"unknown"},{"kind":"Hope","strength":"slight","target":"unknown"}],"constraints":["do_not_infer_cause","do_not_bind_unknown_target_to_player"]}
```

provenance 最清楚，但 punctuation/key 重複增加 prompt；JSON 是**輸入給 Renderer**，不需要模型 structured output 支援。Renderer 是否更守規則需實測。

### S7：額外 LLM wording

翻譯 call input（尚未包含 system message/schema）：

```text
請只將下列 immutable affect facts 改寫成簡潔中文內部狀態，不得新增、刪除或綁定原因、對象、事實、意圖與行為；輸出必須保留每個 kind、strength、target：{"mood":{"label":"Anxious","strength":"moderate","valence":"negative","energy":"high","control":"low"},"dominant":{"kind":"Fear","strength":"strong","target":"unknown"},"secondary":[{"kind":"Anger","strength":"moderate","target":"unknown"},{"kind":"Hope","strength":"slight","target":"unknown"}]}
```

假設理想輸出與 S2 相同，該輸出再成為 Final Renderer input。這會同時付出翻譯 input、翻譯 output、Renderer input，並新增一次 TTFT/network/decoding。

### S8：混合分級

- normal known case：使用 S4，不呼叫額外 LLM。
- long-tail case：只在明確 policy 允許時，把 validated facts 送 wording layer。
- unknown enum 仍不得猜語意；若 wording layer 只是把 `FutureNewEmotion` 原樣包裝，收益可能不足以抵銷額外 call。

S8 的成本是 `normal deterministic cost + routing_rate × wording cost`，必須量測實際 routing rate，不能假設長尾很少。

## 靜態量測方法與結果

### 方法

在隔離的 V8 計算：

- UTF-8 bytes：逐 Unicode code point 依 UTF-8 1/2/3/4-byte 規則加總。
- Unicode chars：code point 數。
- 未呼叫任何模型、未讀 API key、未產生費用。
- 沒有使用 provider tokenizer，因此**不宣稱 exact tokens**。

### 結果

| 樣本 | UTF-8 bytes | Unicode chars | 粗略 token 範圍* | 額外模型 call |
|---|---:|---:|---:|---:|
| S1 enum text | 126 | 126 | 28–50 | 0 |
| S2 中文短語 | 201 | 67 | 55–85 | 0 |
| S3 controls | 99 | 99 | 25–40 | 0 |
| S4 分層語法 | 252 | 84 | 70–105 | 0 |
| S5 模板變體 | 231 | 77 | 65–95 | 0 |
| S6 compact JSON | 372 | 372 | 90–150 | 0 |
| S7 wording input | 498 | 392 | 150–240 | 1 |
| S7 ideal output / renderer input | 201 | 67 | 55–85 each | 同一額外 call 的 output |
| S8 normal | 252 | 84 | 70–105 | 0 |
| S8 long-tail input（較小例） | 238 | 182 | 65–110 | 1 when routed |

\* token range 只用來做敏感度分析，不是 tokenizer 結果。中文、英文 key、punctuation 與 model tokenizer 都會改變值；正式帳務以 API response `usage.prompt_tokens/completion_tokens` 為準。

### 可重現量測邊界

bytes/chars 是精確且可重現的；token range 是人工保守區間。後續若建立 provider-specific tokenizer harness，必須記錄 tokenizer 名稱、版本、chat template 與 special tokens，否則「exact」仍不可比較。

## 成本敏感度（非預測）

只為看量級，使用 2026-08-17 Groq 頁面列出的 qwen input `$0.60/M`、output `$3.00/M`。假設一百萬次 chat，每次只增加本表 affect tokens：

| 方案 | affect 邊際成本範圍 / 1M chats | 計算內容 |
|---|---:|---|
| S1 | `$16.8–30` | 28–50M input tokens |
| S2 | `$33–51` | 55–85M input tokens |
| S3 | `$15–24` | 25–40M input tokens |
| S4 | `$42–63` | 70–105M input tokens |
| S5 | `$39–57` | 65–95M input tokens |
| S6 | `$54–90` | 90–150M input tokens |
| S7 | `$288–450` | wording 150–240M input + 55–85M output + renderer 55–85M input |
| S8 | base `$42–63` + `routing_rate × wording增量` | routing rate 未知 |

這些數字不含 system prompt、記憶、對話、Final Renderer output、cache、retry、reasoning tokens、匯率或價格變更，不可拿來當預算承諾。它只證明 S7 的主要成本不是最後那段文字，而是多一次生成 output。

## 延遲模型

Deterministic S1–S6 的 translator 應是 process-local mapping/serialization，預期不增加 network/TTFT；真正數字仍需 Go benchmark。

S7 額外延遲下界：

```text
extra_latency = network_round_trip + TTFT + wording_output_tokens / generation_TPS
```

若只把 Groq 頁面的約 500 TPS 代入 55–85 output tokens，decoding 本身約 `0.11–0.17s`；這**不是總延遲**，還沒加 network、queue、TTFT、retry。對本地 LM Studio，TPS 取決於模型、量化與硬體，不能沿用 Groq 數字。

S8 的期望額外延遲：

```text
E(extra_latency) = routing_rate × E(wording_latency | routed)
```

但 p95/p99 仍會出現完整 wording latency；低平均值不能掩蓋長尾互動卡頓。

## 結構化輸出能力校正

### Groq qwen/qwen3.6-27b

- 官方 capability table 支援 JSON mode。
- Groq Structured Outputs 頁面的 strict/best-effort model list都未列 qwen；「能產 valid JSON object」不等於「符合我們的 JSON Schema」。
- 即使改用 strict-supported GPT-OSS，schema 也只能保證 `kind/strength/text` 欄位存在，不能證明 `text` 沒把 unknown target 寫成玩家。

### LM Studio

- local server 官方文件支援 JSON Schema constrained output。
- 實際支援度仍受載入模型/grammar/backend 影響，需 integration test。
- 同樣不能用 schema 驗證自由文字的事實忠實度。

因此 S7 所謂「後置 validator」至少需：

1. exact echo of immutable fields；
2. banned internal terms/IDs；
3. target reference allowlist；
4. semantic regression fixtures；
5. validation fail 時回 deterministic S2/S4，而不是 retry 到成功為止。

即使如此，validator 也很難形式化證明沒有委婉新增動機。

## 非付費比較 harness 設計

```text
fixtures/*.json
  neutral
  baseline_only

  mixed_target_unknown
  mood_emotion_conflict
  unknown_enum
  paused
  malformed_partial

for each fixture × deterministic strategy:
  decode wire
  map domain
  render context 1000 次
  assert byte-identical
  count bytes/runes/lines/fields
  scan forbidden facts/IDs/numbers/internal terms

  disabled by default
```

本輪只做靜態量測與設計，沒有新增測試程式；第 05 輪先建立手工 fixture 評分規格，避免先寫 harness 再補驗收標準。

## 與前三輪的差異

1. 八方案從抽象名稱變成同一 snapshot 的具體 payload。
2. token/cost 不再只寫「較高/較低」，而是分開精確 bytes/chars、粗略 tokens 與敏感度成本。
3. S7 的結構保證依實際 provider/model 修正：目前 Groq qwen 不是 strict schema model。
4. S8 的成本/延遲改用 routing rate 公式，不再用「偶爾才呼叫」含糊帶過。
5. 加入可離線重現的 harness 與 provider-specific usage/latency 記錄需求。

## 風險與失敗模式

- **假 exact token**：不記 tokenizer/chat template 就報精確 token，會讓成本結論失真。
- **只看平均 latency**：S8 的 routed 長尾仍會卡住特定玩家回合。
- **schema 崇拜**：JSON 合法不代表文字忠實；echo fields 正確也不代表 prose 無新增。
- **preview model 風險**：Groq 目前把 qwen3.6-27b 列為 preview，能力/價格/可用性可能變動。
- **S6 prompt injection confusion**：JSON 中的 raw unknown label 若可由外部控制，必須 escape、長度限制並視為 data。
- **模板等價性漂移**：S5 的「反應能量」已比原始 arousal 多一層行為含義。
- **成本忽略 retry**：S7 schema/semantic fail 的 retry 會放大 output cost與延遲。
- **雙重自然化**：S7 先 wording、Final Renderer 再 wording，可能同時消耗 token又增加語意漂移。

## 本輪改良

- 為八方案建立同源可比較 payload。
- 精確量測 bytes/chars，將 tokens/成本明確標為區間與敏感度分析。
- 用官方模型 capability 修正 S7 的 schema 假設。
- 建立 deterministic 與 optional model eval 的非付費優先 harness 設計。
- 完整填入九個需求維度，但不做總分或提前淘汰。
- 未修改程式、設定、API key，也未呼叫付費模型。

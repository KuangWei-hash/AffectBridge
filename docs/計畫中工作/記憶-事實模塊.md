# 記憶－事實搜尋模塊

> **狀態：延後（Deferred）。**
>
> 這是讓角色真正形成連續生命、經驗與人際認知的核心系統，對專案長期目標非常重要。但它的資料分區、搜尋、事實整理、衝突處理、記憶寫入與知識邊界會形成一個大型子系統，現階段不實作。
>
> 本文只保留從 `docs/最後一層renderer.txt` 反推出的初步方向，作為未來重新啟動設計時的起點，不代表已定稿的 schema、資料庫或實作計畫。

## 現階段決策

- 不建立記憶資料庫、index 或專責搜尋器。
- 不實作事實排序、衝突處理、記憶寫入或關係演算。
- Renderer 的記憶、認知、關係、事件與情境行為欄位先使用空值。
- 角色仍以當前玩家輸入、基本角色設定、ALMA 情緒與 Renderer 生成回應。
- 現階段只保留「未來可接入」的邊界，不因本文的初步設計而提前建立空 package 或過度抽象。

未來重新啟動本模塊時，必須先重新審查本文的所有假設，再將狀態從 `Deferred` 改為 `Active Design`。

## 目的

角色的記憶、認知、關係、事件與表現習慣會分散在多個資料庫或資料區塊。記憶－事實搜尋模塊負責：

1. 根據本輪玩家輸入規劃需要查詢的記憶區塊。
2. 將查詢分派給各區塊的專責搜尋器。
3. 將候選結果正規化、去重、排序並處理時間與衝突。
4. 組裝成 Renderer 可直接使用、但仍保留語意邊界的結構化 context。

核心目標不是「找到最多資料」，而是：

> 在角色當前可知的範圍內，找出與本輪直接相關、來源清楚、時間正確、不會將事實與主觀認知混在一起的最小充分資料集。

這是一個**可選的角色記憶增強模塊**，不是角色運行的必要依賴。沒有安裝、未啟用或整個模塊不可用時，角色仍然可以透過當前玩家輸入、基本角色設定、ALMA 情緒與 Renderer 正常回應；只是所有記憶與事實搜尋欄位都是空的，表現為一個「沒有可用記憶」的角色。

## 在整體架構中的位置

```text
                         Player Input
                              │
                              ▼
                    Character Orchestrator
                       │             │
             SearchRequest              │ appraisal / snapshot
                       ▼             ▼
       記憶－事實搜尋模塊（可選）        ALMA
                       │             │
              RendererContext      AffectSnapshot
                       └──────┬──────┘
                              ▼
                      Final Renderer / LLM
                              │
                              ▼
                       Character Reply
```

記憶－事實搜尋與 ALMA 是並列的內部子系統：

- 本模塊決定角色本輪**知道什麼、相信什麼、記得什麼**。
- ALMA 決定角色本輪的**情緒與心情狀態**。
- Renderer 使用兩者決定**說什麼、願意透露多少、怎麼說**。

本模塊不呼叫、不更新、也不保存 ALMA affective state。

Orchestrator 只依賴穩定的 `MemoryFactSearch` interface。啟用記憶時注入實際搜尋實作；未啟用時注入 `EmptyMemoryFactSearch`，回傳欄位完整但內容為空的 `RendererContext`。Renderer 與 chat pipeline 不需要因此分成兩套流程。

## 從 Renderer 反推的資料區塊

`docs/最後一層renderer.txt` 目前需要以下資料。這些欄位不應只在最後一刻以字串拼接；在搜尋與整理階段必須保持不同類型。

| Renderer 欄位 | 資料區塊 | 語意 | 證據等級 |
|---|---|---|---|
| `summary_10` | 近期對話 | 維持當前對話連貫 | 背景，不是正式長期記憶 |
| `summary_50` | 中期對話摘要 | 保留較長對話主題與未完成事項 | 背景，可能已被壓縮 |
| `summary_all` | 長期對話摘要 | 保留 session 長期走向 | 背景，不取代正式事件記憶 |
| `retrieved_self_cognition` | 自我認知 | 角色如何理解自己 | 主觀認知，不是客觀事實 |
| `retrieved_other_cognition` | 對他人認知 | 角色如何看待當前對象 | 主觀認知，可能是誤解 |
| `relationship_context` | 關係狀態 | 雙方目前的社會與情感關係 | 領域狀態，可由事件演算或直接保存 |
| `retrieved_events` | 事件／情節記憶 | 與本輪話題相關的正式記憶 | 正式記憶，必須帶來源與時間 |
| `retrieved_situational_behavior_and_language` | 情境行為與用語 | 相似情境下的表現傾向 | 風格控制，不是事實來源 |
| `alma_context` | ALMA | 當前心理與情緒狀態 | **不屬於本模塊** |
| `player_input` | 本輪 request | 搜尋查詢與最後回應的目標 | 不是已確立事實 |

### Renderer 目前可能缺少的欄位

目前 template 沒有單獨的「世界／權威事實」與「當前場景狀態」區塊。如果角色對話會依賴遊戲世界資料，應考慮未來新增：

- `retrieved_world_facts`：角色已知、且與本輪相關的世界事實。
- `current_scene_context`：當前位置、在場人物、可觀察物件與正在發生的事件。

在 Renderer 契約正式擴充前，不要把這兩類資料偷塞進 `retrieved_events` 而失去語意邊界。

## 記憶儲存與專責搜尋器

每個區塊使用獨立 repository/searcher interface。底層可以是不同資料庫，也可以在 v1 先共用同一資料庫的不同 table/index；service 不應依賴具體儲存技術。

| 儲存／搜尋器 | 主要 key | 搜尋方式候選 | 輸出 |
|---|---|---|---|
| `ConversationSummarySearcher` | character + interlocutor + conversation | 時間窗、層級摘要 | 近／中／長期對話背景 |
| `SelfCognitionSearcher` | character | 語意 + topic + validity | 相關自我認知 |
| `OtherCognitionSearcher` | character + target | 語意 + topic + validity | 對當前對象的相關認知 |
| `RelationshipSearcher` | character + target | 直接 key + 有效時間 | 雙方當前關係狀態 |
| `EventMemorySearcher` | character + participants | 語意 + entity + time + causality | 相關事件記憶 |
| `SituationalPatternSearcher` | character + situation tags | 情境相似度 + 適用條件 | 行為、語氣與用語傾向 |
| `WorldFactSearcher`（待確認） | world + entity + character knowledge scope | 精確 + 語意 + 有效時間 | 角色可知的世界事實 |

搜尋器只回候選資料與排序信號，不直接生成角色回應。

## 核心資料契約

### SearchRequest

上層 orchestrator 交給本模塊的 request 至少需要：

```text
SearchRequest
  character_id          角色身分
  interlocutor_id       當前對象身分
  conversation_id       對話範圍
  player_input          本輪輸入
  current_time          處理時間與有效性判斷基準
  scene                  可選；受信任的當前遊戲場景
  budgets               每區塊候選數、最終項目數與 token 上限
```

`character_id`、`interlocutor_id` 與 `scene` 必須由受信任的 server context 提供，不能讓玩家透過 prompt 僞造，否則會造成跨角色或跨玩家記憶洩漏。

### EvidenceItem

各專責搜尋器的共通候選資料應至少保留：

```text
EvidenceItem
  id                    穩定識別碼
  kind                  conversation / event / self_cognition /
                        other_cognition / relationship / behavior /
                        world_fact / scene
  content               可供後續整理的內容
  character_id          該資料屬於哪個角色的知識邊界
  subjects              涉及實體
  source                資料來源與原始記錄 ID
  occurred_at           事件發生時間（若適用）
  valid_from / valid_to 這份狀態的有效時間
  recorded_at           寫入時間
  confidence            系統對資料準確性的評分
  authority             來源權威等級
  visibility            角色是否知道且允許被檢索
  retrieval_score       本輪相關性分數
```

`confidence` 不能單獨當成真實性。最終選擇必須同時考慮資料類型、來源權威、時間有效性與當前話題。

### RendererContext

本模塊的主要輸出：

```text
RendererContext
  conversation
    recent_summary
    medium_summary
    long_summary
  self_cognition[]
  other_cognition[]
  relationship
  events[]
  situational_patterns[]
  world_facts[]          待 Renderer 契約確認
  scene                  待 Renderer 契約確認

  internal_metadata      不送給 Renderer 的追蹤資料：
    selected_evidence_ids
    rejected_conflicts
    source_versions
    retrieval_timings
    coverage_warnings
```

Renderer prompt 的文字區塊應由單一 assembler 從 `RendererContext` 產生，不讓每個 searcher 各自拼 prompt。

`RendererContext` 的 zero value 必須是合法輸入：所有 summary 為空字串、所有檢索清單為空、relationship 為 unknown。這代表「本輪沒有可用記憶」，不代表玩家所說的事情是 false，也不影響 ALMA 狀態的取得與更新。

## 線上查詢流程

```text
1. ValidateScope
   確認 character / interlocutor / conversation 邊界

2. AnalyzeQuery
   從 player input 抽取 topic、entity、time hint、event hint、situation tags

3. PlanSearch
   決定哪些資料區塊必查、哪些可跳過、每區塊 budget

4. ParallelRetrieve
   平行呼叫各專責搜尋器，各自設 timeout

5. Normalize
   統一為 EvidenceItem，保留類型、來源與時間

6. Resolve
   去重、判斷過期、處理取代關係與明確衝突

7. Select
   依相關性與 token budget 選出最小充分集合

8. Assemble
   按照語意區塊組成 RendererContext
```

各 searcher 可平行，但 Resolver 與 Assembler 必須使用同一次 request 的固定時間基準與資料版本，避免同一個 RendererContext 混入不同時點的狀態。

## 事實選擇與衝突原則

Renderer 不應是事實衝突處理器。本模塊在送出 context 前應先處理可判定的衝突：

1. 先分類，不把世界事實、角色信念、關係狀態與行為風格當成同一種命題。
2. 同類資料先比來源權威與有效期，再比具體性、相關性與新舊。
3. 明確的修正或取代關係優先於單純「較新」。
4. 對話摘要與正式事件記憶衝突時，以正式記憶為準。
5. 角色的主觀認知可以與客觀事實不一致；不要把主觀認知自動「矯正」成客觀事實。
6. 無法安全解決的衝突應標記為 unresolved，保留追蹤資料，不生成第三種解釋。
7. 「沒有找到」代表未知，不是 false，也不能讓 LLM 用常識補完。

## 知識與隱私邊界

這是本模塊的正確性條件，不只是安全附加功能：

- 只檢索當前角色已知或有權知道的資料。
- 不能因為世界資料庫有某件事，就讓所有角色自動知道。
- 對他人的認知必須以 `character_id + target_id` 隔離。
- 關係資料必須明確方向；A 對 B 的信任不等於 B 對 A 的信任。
- 對話摘要與事件記憶必須限定角色、玩家與 conversation scope。
- 搜尋 log 可記錄 evidence ID 與分數，但避免在一般 application log 完整複製私密記憶內容。

## 記憶寫入與更新流程

搜尋只是 read path。完整的記憶系統還需要 write path，但寫入不應由 Renderer 邊回答邊直接修改資料庫。

```text
Player Input + Character Reply + Trusted Game Events
                         │
                         ▼
                 Memory Candidate Extractor
                         │
                  typed candidates
                         ▼
              Validation / Dedup / Ownership
                         │
                         ▼
             Per-block Repository Writers
```

初步原則：

- 玩家說的內容不自動成為客觀世界事實。
- Renderer 生成的角色台詞不自動成為新的權威設定。
- 受信任的遊戲事件可成為客觀記錄；對話中的說法先作為 claim 或角色認知候選。
- 新資料應保留 source、time、ownership 與 supersedes/retracts 關係。
- 摘要是檢索加速層，不應破壞或取代可追溯的原始記錄。

write path 與「何時形成新認知／關係更新」需要另開設計，v1 可先專注於 read/search path。

## 失敗與降級

本模塊的可用性政策是 **fail open to empty memory**：記憶功能不可用不能讓整個角色停止回應。多搜尋器並行時，內部仍必須區分「查無資料」與「資料源失敗」，但兩者對 Renderer 都以空資料區塊表示：

- `empty`：查詢成功但沒有相關資料，Renderer 應將該部分視為未知。
- `unavailable`：資料庫、index 或 searcher 失敗，該區塊降級為空，並在 `internal_metadata.coverage_warnings` 與 metrics 中標記；不對 Renderer 謊稱「角色確定沒有這段記憶」。
- `disabled`：整個模塊或某資料區塊未啟用，由 no-op 實作回傳空區塊。
- 所有記憶區塊都可降級為空；關係缺失時是 unknown，不是停止本輪。
- 角色身分、玩家身分與當前 request 的授權驗證仍由 orchestrator/controller 負責；這些不是記憶降級可以繞過的安全條件。
- 不將資料庫名稱、query、score 或失敗細節放入 Renderer prompt 或玩家回應。

## 初步 interface 邊界

```go
type MemoryFactSearch interface {
    Search(ctx context.Context, req SearchRequest) (RendererContext, error)
}

// EmptyMemoryFactSearch is used when memory is disabled or unavailable.
// It returns a valid empty RendererContext and does not block character reply.
type EmptyMemoryFactSearch struct{}

func (EmptyMemoryFactSearch) Search(
    ctx context.Context,
    req SearchRequest,
) (RendererContext, error) {
    return NewEmptyRendererContext(), nil
}

type BlockSearcher interface {
    Search(ctx context.Context, query BlockQuery) ([]EvidenceItem, error)
}

type FactResolver interface {
    Resolve(ctx context.Context, candidates []EvidenceItem, budget Budget) (ResolvedEvidence, error)
}

type ContextAssembler interface {
    Assemble(resolved ResolvedEvidence) (RendererContext, error)
}
```

`BlockSearcher` 是底層儲存與搜尋技術的 adapter boundary；`MemoryFactSearch` 是 chat pipeline 應依賴的高層介面。

`MemoryFactSearch.Search` 的錯誤是給 orchestrator 記錄與觀測用；上層預設應改用空 `RendererContext` 繼續流程，而不是將記憶 backend 錯誤直接回給玩家。

## 建議的模塊結構

```text
internal/memoryfact/
  request.go                 SearchRequest / Budget
  evidence.go                EvidenceItem / kind / provenance
  context.go                 RendererContext
  service.go                 MemoryFactSearch orchestration
  empty.go                   disabled/unavailable no-op implementation
  planner.go                 query analysis + block routing
  resolver.go                dedup / validity / conflict
  assembler.go               resolved evidence → RendererContext
  searcher.go                BlockSearcher interfaces

  conversation/              summary search adapter
  cognition/                 self / other cognition adapters
  relationship/              relationship adapter
  event/                     episodic memory adapter
  situation/                 behavior and language adapter
  world/                     optional world fact adapter
```

實際 package 是否需要拆到這個粒度，等資料庫與 interface 定稿後再決定。不要為了目錄看起來完整而先建立空 package。

## 待確認的設計問題

1. 每個記憶區塊實際對應哪一種資料庫與 schema？
2. 世界客觀事實是否屬於角色記憶，或是獨立的 world-state service？
3. 如何表示「世界上是真的」與「角色相信是真的」？
4. `relationship_context` 是直接保存的當前狀態，還是由關係事件每次演算？
5. 對話摘要的 10 / 50 / all 是固定 turn 數、動態區段，還是多層 materialized summary？
6. 搜尋器只做 retrieval，還是允許各自使用 LLM 做 query rewrite / rerank？
7. 「角色知道但不願透露」由搜尋模塊過濾，還是全部交給 Renderer 根據關係與情緒決定？
8. 某個資料區塊不可用時，如何記錄 coverage warning 並在不中斷角色回應的前提下降級為空？
9. 事件、認知、關係與行為樣式的 write path 分別由什麼訊號觸發？

## 與其他規劃文件的邊界

- `如何利用LLM.md`：負責 provider-neutral LLM 介接；不負責角色記憶。
- `如何配合ALMA_REST_SERVER.md`：負責情緒運算介接；不負責事實搜尋。
- `最後一層renderer.txt`：負責使用已整理資料生成角色輸出；不重新檢索、不改寫事實、不更新記憶。
